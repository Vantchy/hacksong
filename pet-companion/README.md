# 项目名称：茸学伴（暂定）

> 一个以虚拟宠物形态存在的AI伴学搭子，用"被看见"和"共场陪伴"降低启动焦虑。

---

## 一、产品定位

**一句话定义：** 在你学不进去的时候，有一只电子小动物安静地趴在屏幕边陪着你。

**核心主张：** 不催你、不骂你、不给你列待办清单。它只做三件事——**陪着、听着、反馈着**。

**目标用户：** 期末周启动困难、容易被杂事分心、需要"有人在旁边"才能进入状态的大学生。

---

## 二、核心功能模块

### 模块1：共场陪伴（核心）

**功能描述：** 用户在桌面/网页端开启"共学模式"后，宠物出现在屏幕角落，呈现与用户状态联动的陪伴姿态。

**具体表现：**
- 用户专注时 → 宠物趴着打盹/翻肚皮，偶尔动动耳朵
- 用户走神（长时间无操作/切换无关页面）→ 宠物抬头看你一眼，继续趴下（不打扰，只提醒）
- 用户结束学习 → 宠物伸懒腰、打哈欠，给出简单的收尾反馈

**关键设计原则：** 存在感控制在"余光可见"级别，不遮挡、不弹窗、不闪烁。

### 模块2：状态镜像（"被看见"）

**功能描述：** 学习开始前，用户用一句话告诉宠物"我现在什么状态"，宠物据此给出低门槛启动动作。

**交互流程：**
1. 用户点击宠物 → 弹出简洁输入框："现在感觉怎么样？"
2. 用户输入（如："好烦，不想学""今天状态不错""有点焦虑"）
3. 宠物给出对应回应 + **一个极小的启动动作**

**回应示例：**
| 用户输入 | 宠物回应 | 启动动作 |
|---------|---------|---------|
| "好烦，不想学" | "那先不学，陪我看一分钟窗外吧" | 进入60秒深呼吸/发呆倒计时 |
| "今天状态不错" | "好耶！那今天先做最顺手的那件事？" | 自动推荐今天最简单的一项任务 |
| "有点焦虑" | "你已经在焦虑了，说明你在乎。先写一行字就好。" | 打开空白页，光标定位到第一行 |

### 模块3：状态记录（数据画像入口）

**功能描述：** 每次学习结束后，宠物用极简交互记录本次状态，形成长期画像。

**记录方式：**
- 学习结束后弹出三个表情按钮（😊/😐/😫）→ 点击即完成记录
- 系统自动采集：本次专注时长、中断次数、时间段

**画像维度：**
- 一周内哪个时间段专注最长
- 哪种情绪状态下启动最快
- 连续专注的平均时长上限

### 模块4：长期陪伴演化（加分项）

**功能描述：** 随着数据积累，宠物的行为逐渐个性化。

**演化示例：**
- 连续三天在同一时间学习 → 那个时间点宠物会提前出现在屏幕边等你
- 发现你每次周二下午状态最差 → 周二中午宠物会主动问"下午要不要换个地方学？"
- 发现你专注上限约45分钟 → 第40分钟宠物开始频繁翻身/坐立不安（暗示该休息了，但不打断）

## 三、产品形态

| 维度 | 方案 |
|------|------|
| 载体 | 浏览器插件 + 桌面端小窗（优先浏览器插件，开发成本最低） |
| 宠物呈现 | 2D动态插画风格（类似Live2D），带轻微呼吸动画 |
| 交互方式 | 点击宠物 ↔ 弹出对话/状态界面；拖拽移动位置 |
| 数据存储 | 本地存储（兼顾隐私）+ 可选云端同步 |

## 五、团队分工

| 成员 | 角色 | 负责范围 | 工作分支 |
|------|------|----------|----------|
| **A** | 🎨 UI/视觉工程师 | `index.html` 布局、`css/style.css` 样式、`assets/images/` 图片资源、宠物动画视觉 | `feature/ui` |
| **B** | ⚡ 交互工程师 | `js/app.js` 按钮绑定、状态镜像对话、UI更新、动画触发、专注度检测 | `feature/interaction` |
| **C** | 🔧 集成/数据工程师 | `js/storage.js` 存档管理、`js/gameLogic.js` 游戏算法、状态画像数据；**负责合并PR到main** | `feature/storage` |

### 各成员职责详解

#### A（UI/视觉工程师）
- 负责一切**视觉呈现**：HTML 结构、CSS 样式、宠物表情/动画、整体UI风格
- 实现宠物不同状态（专注/走神/休息）的视觉反馈
- 可以使用纯 CSS 或 Tailwind 等工具
- **不需要关心**交互逻辑如何实现，只需在 HTML 中定义好 `id` 和 `class`
- 工作范围：`index.html`、`css/style.css`、`assets/images/`

#### B（交互工程师）
- 负责一切**用户交互**：宠物点击事件、状态镜像对话流程、UI 渲染、动画触发
- 实现"走神检测"（浏览器标签页可见性API + 鼠标键盘空闲检测）
- 通过调用 `gameLogic.js` 中的方法获取计算结果，调用 `storage.js` 的 `save/load` 函数读写存档
- **不需要直接操作** localStorage，也不负责算法公式
- 工作范围：`js/app.js`

#### C（集成/数据工程师）
- 负责**底层能力**：数据持久化（localStorage）、游戏算法（等级成长、经验计算、属性衰减）
- 负责**状态画像数据**：学习时长记录、情绪标签、专注趋势统计
- 同时担任**项目管理员**：创建仓库、管理 main 分支、审核并合并 A 和 B 的 PR
- 工作范围：`js/storage.js`、`js/gameLogic.js`、`.gitignore`、`README.md`

## 六、分支策略

采用 **功能分支 + 专人合并** 的模式，避免三人并行开发时的代码冲突。

```
main 分支（成品仓库 — 仅 C 可合并）
  ↑
  ├── feature/ui           （A 的私人工作间）
  ├── feature/interaction  （B 的私人工作间）
  └── feature/storage      （C 的私人工作间）
```

### 工作流程

```
1. 初始化
   C 创建仓库 → push 初始代码到 main

2. 各成员拉取分支
   A: git checkout -b feature/ui
   B: git checkout -b feature/interaction
   C: git checkout -b feature/storage

3. 并行开发
   三人在各自分支上独立工作，互不干扰

4. 合并（由 C 执行）
   Step 1: 审核 A 的 PR → 合并 feature/ui → main
   Step 2: 审核 B 的 PR → 合并 feature/interaction → main
   Step 3: 如有冲突，C 手动解决
```

### 为什么这样设计？

| 问题 | 解决方案 |
|------|----------|
| A 改样式时不小心改坏了 B 的交互代码 | 各自在独立分支工作，互不影响 |
| 三人同时修改 `index.html` 导致冲突 | C 最后统一合并，只需解决一次冲突 |
| A 改按钮样式，B 改按钮功能 | 改的是同一按钮，但在不同分支，C 合并时协调 |
| 代码质量谁来把关 | C 作为管理员审核 PR，确保质量 |

## 九、判断产品是否成功的标准

以下四个问题，回答"是"的次数越多，产品越成功：

1. 用户是否**不需要意志力**就能启动学习？（打开浏览器，宠物已经在了）
2. 用户是否**不觉得被监视**，反而觉得被陪伴？（宠物在的时候不烦躁）
3. 用户是否在某个时刻**意识到"哦它好像了解我了"**？（宠物行为开始和用户习惯对齐）
4. 用户是否在**不想学的时候愿意先点开宠物**，而不是直接关掉？
